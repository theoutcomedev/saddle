# Agent Note: 聊天中的文件链接只进入面板，不再交给桌面

Status: implemented

[English](2026-09-13-chat-file-links-route-to-the-pane.md) | 中文

## Problem

对话里的文件路径——工具行摘要、产物文件标签，或收尾消息中的提及——会先进入 Workbench 文件面板，随后又请 Host 把同一路径交给桌面的默认应用。在本地 GUI 上，后半段会在已经显示该文件的面板旁边启动读者自己的编辑器，于是一次点击产生两个界面。在容器化或无头 Host 上，同一次调用只可能失败——这也正是聊天视图带有一个页面内拒绝对话框、并对同一路径提供重试的原因。一个手势的两半对「文件去哪里」给出不同答案时，就需要一个拒绝界面来解释那无法普适的一半。

## Decision

`ChatViewInjected.openFile` 把路径按会话 cwd 解析后派发 `workbench:open-file`，并打开详情列。它不再调用 `WorkspaceRuntime.openPath`，也不返回可等待的值，因此聊天视图不再包裹它。拒绝对话框、其文案（`fileOpen.*`）、样式、包级测试与 golden 快照都随这次调用一并删除。

`host.openPath` 及其平台适配保持不变，仍可从 Workbench 文件面板自身的「打开」控件到达——那是在文件所在之处、指名要求桌面接管的手势。行内路径链接仍然阻止事件冒泡，因此链接与行的展开开关依旧是两个互不干扰的手势。

## Alternatives considered

**保留两个目标，让读者关掉桌面交接。** 一个偏好项会让默认的双开继续存在，而且要先有这个设置项才能消除困扰。面板本就通过一个显式控件提供桌面交接，因此让隐式的那一份消失并不会损失能力。

**为面板自身的「打开」控件保留拒绝对话框。** 该控件就在读者主动打开的面板里、紧邻文件；一个能跨视图切换存活的会话级模态，对一次本地拒绝来说是错误的归属。面板控件维持现有的静默失败行为。

**只把该手势交给桌面。** 面板是文件内容及其邻居所在之处，也是在所有 Host 形态（包括远程与容器化）下都能工作的目标。舍弃它会为了保留失败的一半而移除可用的一半。

**保留对话框，只从聊天手势中移除该调用。** 该对话框只能由那次调用的拒绝触发；继续接线会留下任何产品路径都到不了的界面。

## Consequences

文件路径点击现在在所有 Host 上只有一个结果：文件出现在 Workbench 中。本地双开消失，远程或容器化部署也不会再为一次在面板中已成功的点击报错。代价是：用读者自己的应用打开文件需要多一步面板上的「打开」控件，而会话界面不再上报 Host 拒绝。若要重新引入会话级的桌面交接，拒绝界面必须随之回归——同一路径的原因与重试，以及防止在关闭后到达的结算重新打开对话框的请求代次保护。
