# Agent Note: 工作区模式：一个机制、三个入口、一条记录

Status: implemented

[English](2026-09-13-workspace-modes.md) | 中文

## Problem

外壳只有一种形状。长文阅读、写作、查看 agent 的工作、或者玩点什么的人，得到的都是同样的三列；唯一的改变方式是手动拖拽面板——每个会话、每台设备都要重来。更深的问题在架构上：所有本可以是「模式」的东西（全屏画布、workbench dock、移动端抽屉）都是各自独立的功能、各自独立的状态，于是第二种形状意味着第二套机制，第三种意味着第三套。

agent 完全无法改变形状，而这对一个「软件围绕工作重新排布自身」的产品来说是本末倒置。

## Decision

**模式是数据。** 目录用布局服务自己的词汇描述排布——每个面板为 `closed` / `default` / `wide`——宽度契约仍留在 `ui-layout` 的 columns 里。新增一个模式只是一条记录加它的文案，面板数值从不离开外壳：模式说的是形状，不是尺寸。

**应用一个模式是两次写入、没有生命周期变化。** `ctx.layout.setPanels` 排布面板（关闭走关闭动作，因为宽度 setter 会把 0 夹回打开区间），根元素上的一个属性——`data-workspace-mode`——把模式交给样式。详情子树本就以 0 宽度保持挂载，这里也不挂载或卸载任何东西，因此「切换不丢状态」是事实而不是期望。

**记忆按设备类别。** 当前模式持久化在 `phone` / `tablet` / `desktop` 的 store 作用域键下：刷新后恢复该设备类别离开时的形状，手机与笔记本可以各自不同。

**三个入口，同一张脸。** 侧边栏底部、Deployments 与 Scheduled Tasks 旁边的「模式」行；会话头部一键退出的当前模式 chip；以及模型的 `set_workspace_mode` 工具。三者调用同一个注入的 `apply`。

**agent 的入口是一条日志事件，而不是一个设置。** `@deepseek-ai/dsh-workspace-modes` 拥有工具与 `workspace/mode` 事件；宿主把它折叠成携带 `{ mode, at }` 的 `workspaceMode` 会话投影，其中 `at` 是记录它的事件序号。chip 按序号把每条指令消费一次：针对同一模式的两条请求是两条指令（退出之后再说「让我回到 zen」依然生效），而已经消费过的指令永远不会撤销用户的退出。用户自己的切换直接写入 store，不经过日志往返。

**agent 可以自行应用模式**——不限于显式请求。同一次改动里有四条护栏：它总是说明自己应用了什么（工具结果加 chip）；退出只需一次点击，且永远不会被当初进入它的指令撤销；切换不损失状态；记录在无人查看的会话里的指令，会在该会话被打开时生效。

## Alternatives considered

**每种形状一个组件树。** 最直观的第一版实现——一个渲染自己外壳的 zen 组件——会让每个模式变成一套并行外壳，第三种模式就要同时维护两套机制。配方形式只保留一套外壳和一个排布步骤。

**模式只做浏览器端偏好。** 只存在客户端会让 agent 完全无法改变它，也让「谁改了我的屏幕」无从追溯。事件在日志里，客户端只是它的消费者。

**让 agent 只能建议。** 产品负责人否决：agent 可以切换。上面的护栏正是让这件事安全的东西——一次没有说明的改排、或一次会丢状态的改排，是这个决定必须避免的失败。

**用模式自己的 CSS 类驱动排布，而不是布局 store。** CSS 关不掉让步求解器拥有的网格轨道，第二个几何权威会在每次缩放时与现有权威冲突。模式通过与拖拽手柄相同的动作写入。

**为撤销保存切换前快照。** 回退到记忆形状会让「退出这个模式」变成「恢复当时的任何东西」，而一个模式的退出同时也是它自身的标准定义；普通模式就是外壳自己的默认形状。

## Consequences

外壳从此有了形状词汇而不是单一布局：已交付三个模式（standard、focus、zen），后续模式是目录记录而不是功能。排布按设备类别跨刷新存活，agent 也能改变它——记录在会话日志中，因此重放、第二个标签页与冷读结果一致。

代价：现有模式不能改变外壳的内容（三者都只是重排面板与阅读宽度）；模式不能叠加，Focus 还不是其他模式的子状态；退出模式恢复的是外壳默认而不是某个记忆中的排布；模式的排布不在宿主侧验证，因此未运行的客户端会在下次加载时应用挂起的请求。
