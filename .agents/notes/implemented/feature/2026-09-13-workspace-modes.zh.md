# Agent Note: 工作区布局：一个机制、九种形状、一条记录

Status: implemented

[English](2026-09-13-workspace-modes.md) | 中文

## Problem

外壳只有一种形状。长文阅读、写作、查看 agent 的工作、或者玩点什么的人，得到的都是同样的三列；唯一的改变方式是手动拖拽面板——每个会话、每台设备都要重来。更深的问题在架构上：所有本可以是「模式」的东西（全屏画布、workbench dock、移动端抽屉）都是各自独立的功能、各自独立的状态，于是第二种形状意味着第二套机制，第三种意味着第三套。

agent 完全无法改变形状，而这对一个「软件围绕工作重新排布自身」的产品来说是本末倒置。而已有的形状在手机上根本无法成立：它们只是移动面板宽度，而手机没有面板宽度可移。

## Decision

**布局是数据。** 一条目录记录就是一份 `ShellSpec`——每个面在哪里（`column` / `sheet` / `none`）、是否在屏幕上、详情面板的宽度档、头部装饰、输入框形状、疏密，以及阅读栏宽——再加上哪些设备类别的选择器提供它。新增一个布局就是一条记录加它的文案，永远不需要在外壳里另开一条代码路径；像素宽度留在 `ui-layout` 的 columns 里：布局说的是形状，不是尺寸。已交付九个：`default` 与 `focus` 面向所有类别，`capture` 与 `read` 面向手机，`zen` 与 `workbench` 面向平板到桌面，`counter` 面向平板，`studio` 面向笔记本与桌面，`wall` 面向桌面。

**设备决定什么能成立；外壳永不丢弃请求。** `ctx.device`（ui-layout）按窗口最短边分类——`phone`、`tablet`（仅触摸）、`laptop`、`desktop`——把输入方式作为独立的一条轴，并把类别、输入画像、面板能否并排停靠作为 `data-device`、`data-input`、`data-panes` 发布在根元素上。`resolveShell` 在渲染之前就把规格针对这些事实解算：在无法并排停靠面板的设备上，`column` 变成盖在工作之上的 `sheet`；当布局要求在正文旁边放面板、列宽又装不下两者时，先让会话列表退到它的控制栏，而不是把面板变成抽屉。两种退让都不会改写已存储的宽度，因此窗口变宽后恢复的是用户自己的几何。这正是这个能力存在要守的规则：布局是对「人现在应该看到什么」的主张，外壳必须让它成立。

**应用一次是一次调用，没有生命周期变化。** `ctx.layout.applyShell(spec)` 写入规格以及它蕴含的开关状态，根元素上的一个属性——`data-workspace-layout`——把布局交给样式。详情子树本就以 0 宽度保持挂载，这里也不挂载或卸载任何东西，因此「切换不丢状态」是事实而不是期望。

**记忆按设备类别，而且会跟随类别变化。** 每个类别上次显示的形状按类别记在 store 自己的状态里，因此手机与笔记本可以各自不同，刷新后恢复的是该类别的形状。store 跟随 `ctx.device`，而不是在加载时只读一次：被拖进手机档位的窗口，会用同一份事实同时切换记忆中的布局与选择器列表，以及外壳的排布。

**三个入口，同一张脸。** 侧边栏底部、Deployments 与 Scheduled Tasks 旁边的「布局」行（在没有侧边栏列的设备上，它位于会话列表抽屉内）；会话头部一键退出的当前布局 chip；以及 agent 的 `set_workspace_layout` 工具。三者调用同一个注入的 `apply`。

**agent 的入口是一条日志事件，而不是一个设置。** `@deepseek-ai/dsh-workspace-modes` 拥有工具与 `workspace/layout` 事件；宿主把它折叠成携带 `{ layout, at }` 的 `workspaceLayout` 会话投影，其中 `at` 是记录它的事件序号。chip 按序号把每条指令消费一次：针对同一布局的两条请求是两条指令（退出之后再说「让我回到禅写」依然生效），而已经消费过的指令永远不会撤销用户的退出。用户自己的切换直接写入 store，不经过日志往返。

**移除不等于拒绝。** 布局可以把某个面拿走，而用户的手势依然能拿回它：显式打开会盖过 `none`，这就是为什么在写作布局里点一个文件会打开面板，而不是什么也不发生。

**词汇是布局，而不是 mode。** 产品里早就有 agent preset——那是助手能做什么——头部会把它显示成一枚 pill。把这个能力也叫做 mode，会让同一个头部出现两枚同名 chip、同一个侧边栏出现两行共用同一个词，而这是用户无法绕开的命名缺陷。所有可见之处都叫 **布局**：侧边栏行、选择器标题、chip、工具（`set_workspace_layout`）、会话事件（`workspace/layout`）与投影（`workspaceLayout`）；普通布局的 id 是 `default` 而不是 `standard`，与 Standard preset 冲突的那个词因此消失。包名保持发布时的样子——真正要改的是人读到的名字。

**agent 可以自行应用布局**——不限于显式请求。同一次改动里有四条护栏：它总是说明自己应用了什么（工具结果加 chip）；退出只需一次点击，且永远不会被当初进入它的指令撤销；切换不损失状态；记录在无人查看的会话里的指令，会在该会话被打开时生效。

## Alternatives considered

**每种形状一个组件树。** 最直观的第一版实现——一个渲染自己外壳的 zen 组件——会让每个布局变成一套并行外壳，第三种就要同时维护两套机制。规格形式只保留一套外壳和一个解算步骤。

**保留宽度运算，给每台设备各配一套断点。** 十四个 CSS 断点与五个 JavaScript 阈值早已对「什么算手机」各执一词（768 对 1024），因此布局问不出外壳能回答的问题。一次分类、以属性发布，才让布局在手机上真正有意义。

**在一个布局内为每个设备类别各写一份规格。** 那样每个布局都要为每个类别携带一份规格，目录会按「类别 × 布局」增长，而没有任何东西维持这些变体之间的一致性。一份规格加一个会替换摆放位置的解算器更小，也把诚实规则收在一个地方。

**丢弃被请求的面，而不是替换它。** 改动前的行为——面板在手机上、在竖屏平板上干脆不打开——正是让一个能用的布局看起来坏掉的原因。替换（盖在工作之上的抽屉）在两个方向上都是同一套机制：外壳无法按原样渲染的请求，依然是一个「想看到它」的请求。

**布局只做浏览器端偏好。** 只存在客户端会让 agent 完全无法改变它，也让「谁改了我的屏幕」无从追溯。事件在日志里，客户端只是它的消费者。

**让 agent 只能建议。** 产品负责人否决：agent 可以切换。上面的护栏正是让这件事安全的东西——一次没有说明的改排、或一次会丢状态的改排，是这个决定必须避免的失败。

**把两个概念都叫 mode。** 设计文档称其为 mode，第一版实现也照做，于是上线的头部把「标准模式」（preset）与「标准模式」（布局）并排显示成两枚读者无法区分的 chip。重命名这个概念比给它加注解更便宜。

**用布局自己的 CSS 类驱动排布，而不是布局 store。** CSS 关不掉让步求解器拥有的网格轨道，第二个几何权威会在每次缩放时与现有权威冲突。布局通过服务写入规格；拖拽手柄则继续通过同一个 store 写入几何。

**为撤销保存切换前快照。** 回退到记忆形状会让「退出这个布局」变成「恢复当时的任何东西」，而一个布局的退出同时也是它自身的朴素定义；普通布局就是外壳自己的默认形状。

## Consequences

外壳从此有了形状词汇而不是单一排布：已交付九个布局，每个只提供给那些「该做这件事」的设备类别，后续布局是目录记录而不是功能。哪些面存在、它们在哪里、留多少装饰、输入框长什么样、留多少白、正文多宽，全都是数据。在手机上差异如今可见（速记保留输入框并把会话列表拉到工作之上；阅读把输入框撤走，直到你叫它回来），在横屏平板上详情面板并排停靠，而不是无声地拒绝打开。排布按设备类别跨刷新存活，agent 也能改变它——记录在会话日志中，因此重放、第二个标签页与冷读结果一致。

这次改动删掉了外壳样式表里十六个 `max-width` 块、侧边栏自动收起阈值，以及剩下四处 JavaScript 宽度判断；外壳关于设备的答案现在集中在一处，CSS、点击处理与布局都读它。

代价：布局不能叠加，Focus 还不是其他布局的子状态；一个布局对它所提供的每个设备类别只有一份规格，因此平板上的 `workbench` 与桌面上的差异完全来自解算器；未做过选择的设备类别得到朴素布局，而不会继承别的类别的选择；退出布局恢复的是外壳默认而不是某个记忆中的排布；布局的排布不在宿主侧验证，因此未运行的客户端会在下次加载时应用挂起的请求。
